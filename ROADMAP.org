* E2EE

The old libolm-based MITM-proxy approach is deprecated upstream (its
best-known implementation was archived on 2026-04-08).  State of the
ecosystem as of 2026-09:

+ *vodozemac* 0.11.0 (pure Rust): the reference implementation of
  Olm/Megolm, audited; also provides SAS and MSC4108 verification.
+ *matrix-rust-sdk*: production-ready client SDK (Element X, Fractal,
  iamb, Robrix).  Its ~matrix-sdk-crypto~ crate is a standalone
  encryption state machine with no network I/O: callers feed it
  to-device messages and encrypted events, and it returns decrypted
  events plus outbound requests (key distribution) to send.
+ *libolm*: deprecated upstream; only old clients still use it.
+ *Element*: Web/Desktop uses matrix-js-sdk + Rust crypto compiled to
  WASM (matrix-sdk-crypto-wasm); Element X uses matrix-rust-sdk via
  UniFFI bindings (Kotlin/Swift; Python/Ruby for crypto-ffi).
+ *FluffyChat*: Rust FFI natively, vodozemac WASM on web.
+ *Spec v1.19* (2026-07): proper history sharing when joining
  encrypted rooms; QR/emoji verification via MSC4108 in vodozemac.

Design decision needed first:

1. *Subprocess agent around matrix-sdk-crypto* (preferred): a small
   Rust binary speaking line-delimited JSON over stdio, holding the
   crypto state machine and a SQLite store; Emacs feeds sync
   to-device events and m.room.encrypted events, receives decrypted
   events and outbound requests, and performs the requests via
   ~leman-api~.  Mirrors how the official wasm/Node bindings work;
   no Emacs module compilation issues; crash-isolated; needs the Rust
   toolchain to build (not currently installed).
2. *Dynamic module (C FFI)*: thin C shim over matrix-sdk-crypto or
   vodozemac, loaded via the Emacs module API.  In-process and fast,
   but requires maintaining C glue + module lifecycle discipline, and
   bindings for the full state machine are not trivial.

Phasing:

1. *Decrypt-only* ("E1"): agent + sync integration; encrypted rooms
   readable, placeholders for undecryptable events.  DONE 2026-09-12.
   + Working: agent subprocess (matrix-sdk-crypto 0.18, SQLite store),
     sync integration (to-device events, device lists, OTK counts fed
     before ~next_batch~ is persisted), outgoing request pump
     (keys/upload, query, claim, sendToDevice, signature upload),
     decryption of live and retro events, placeholder rendering,
     identity/OTK key uploads, room key receipt, cross-client
     interoperability (Element, FluffyChat) verified on a real
     homeserver.
   + Deferred: retrying undecryptable events when keys arrive later
     (needs key backup, E4, to be useful).
   + Lessons learned, worth keeping:
     - Elisp cannot represent empty JSON objects: ~json-serialize~
       encodes nil as ~{}~ while ~json-encode~ encodes it as ~null~.
       Server-bound payloads must never be round-tripped through
       elisp; the agent passes request bodies as pre-encoded JSON
       strings and the client performs them verbatim.
     - Saved sessions must fetch the device ID (whoami) before
       starting the agent; the crypto store is keyed by device, so a
       nil device ID silently disables E2EE.
     - The live sync path deduplicates events by ID (re-delivery
       after a limited timeline otherwise shows duplicates).
     - Waiting for an agent reply must pump only the agent's
       output; processing homeserver responses inside such a wait
       nests arbitrary agent requests (the 2026-09-15 verification
       hang).
2. *Encrypt-send* ("E2"): send encrypted messages, automatic key
   distribution to member devices.  DONE 2026-09-13.
   + Working: ~encrypt_room_event~ (Olm session claiming, room key
     sharing, Megolm encryption), send flow wired into
     ~leman-send-message~ (messages and emotes) with a synchronous
     request pump, fail-closed sending (no plaintext into encrypted
     rooms), warning when a room has encrypted traffic but encryption
     is inactive.  Verified against Element and FluffyChat on a real
     homeserver.
   + Follow-up: encrypt reactions (m.reaction) and other non-message
     event types in encrypted rooms.
3. *Verification* ("E3"): emoji SAS verification of devices.
   DONE 2026-09-15.
   + Working: the full SAS dance over to-device events —
     ~devices~, ~request_verification~/~verification_requests~,
     ~accept_verification~, ~start_sas~, ~accept_sas~,
     ~verification_sas~ (emoji), ~confirm_sas~,
     ~cancel_verification~ — plus the interactive ~leman-e2ee-verify~
     command (accepts incoming requests, shows the emoji prompt,
     confirms or cancels, pumps outgoing requests throughout).
     A round-trip test drives both sides of the dance through the
     protocol (agent <-> an in-process second machine).
     Private cross-signing keys are imported from secret storage
     (~import_cross_signing_keys~), and every decryption returns
     the sdk's authenticity ~shield~ state, rendered per message.
     Session keys can be exported/imported in Element's format.
   + Until the user verifies, other clients still show the
     "device not verified" warning; after verification it goes away.
   + Follow-up: QR verification.
4. *Key backup* ("E4"): Megolm backup v1 plus secret storage (SSSS).
   DONE 2026-09-15, user-tested against a real conduit-family
   homeserver.  The agent creates/imports the backup decryption
   key, backs up and imports room keys, and encrypts/decrypts SSSS
   secrets; the client performs the HTTP calls, drives the setup
   (~leman-e2ee-setup-backup~) and restore (~leman-e2ee-restore-keys~,
   ~leman-e2ee-restore-old-backup~) flows, inspects state
   (~leman-e2ee-backup-dump~), deletes stale versions, and pumps
   room-key backups after syncs.  Room keys are also gossiped: a
   decryption failure queues an ~m.room_key_request~ to the user's
   own verified devices, which auto-forward the missing keys.
   Element interoperates (standard ~m.megolm_backup.v1~ secret,
   SSSS default key).
   + Conduit quirks worked around: the lexicographic "latest"
     backup version (post-create verification + stale-version
     deletion) and the missing ~GET /room_keys/versions~ list
     endpoint.

TDD workflow (tests before code; monorepo, agent in ~e2ee/~):

1. *Spec first*: ~e2ee/PROTOCOL.org~ pins every request/response
   shape (one JSON object per line; ~{"id":N,"cmd":...}~ ->
   ~{"id":N,"ok":...}~ / ~{"id":N,"err":...}~; ~hello~ does version
   negotiation).
2. *Rust tests* (~cargo test~) using ~matrix-sdk-test~ fixtures
   (the same alice/bob integration style as matrix-sdk-crypto): a
   two-machine key exchange and encrypt/decrypt round trip driven
   through the *protocol layer*, plus framing, error mapping, and
   store persistence across agent restarts.
3. *Elisp tests* (ERT) against a fake in-memory transport: request
   id correlation, timeouts, error mapping, sync hook (to-device
   events processed before persisting ~next_batch~).
4. *Contract fixtures*: shared JSON fixtures (vendored from
   matrix-sdk-crypto test data) run through both implementations
   must agree.

* UI rework plan

Goal: /Element's information architecture + Magit's interaction model +
Org's folding + Transient's menus + svg-lib's visual polish + Emacs's
text and navigation semantics./

Inspirations to draw from (not to copy): Magit (contextual operations,
point-driven menus), Treemacs (sidebar behavior), Elfeed/notmuch/mu4e
(message-oriented navigation), Org (folding, structured documents),
Casual/Transient (discoverability), svg-lib (visual vocabulary beyond
faces and ASCII).

Design constraints:

+ Keep EWOC for room buffers (it is what makes them scale).
+ Everything stays selectable, searchable text underneath the polish.
+ Window layouts must remain bookmarkable (e.g. Burly).

Phases:

** Phase 1: Sidebar
Side-window ~*Leman Sidebar*~ on the left: magit-section room list
(reusing taxy grouping: favorites, low-priority, DMs, spaces), room
avatars, svg-lib unread badges (distinct mention badge), topic snippet.
RET/click to view; auto-follow recent activity.  Dedicated window that
survives ~delete-other-windows~.

** Phase 2: Messages as Magit sections
Each event a magit-section in room buffers: ~n~/~p~/~M-n~/~M-p~ section
motion, point-driven context.  Split the room transient into a message
transient (react, reply, thread, edit, redact, copy link), with
unavailable actions grayed out per event type.

** Phase 3: Org-style folding
Threads foldable inline at the root message (the thread view buffer
remains for the focused case); date headers and coalesced
membership-event runs collapsible.

** Phase 4: svg-lib polish
svg-lib tags/badges/chips for header-line room state (encryption,
notification mode), typing indicator, connection status, and the
reaction picker.
