#+TITLE: Leman E2EE Agent Protocol

The protocol between Leman.el (the client) and the ~leman-agent~
subprocess (the agent), which wraps the ~matrix-sdk-crypto~ state
machine.  Protocol version 1.

* Framing

+ One JSON object per line, UTF-8, over the agent's stdin/stdout.
+ Requests (client -> agent): ~{"id": N, "cmd": "...", "params": ...}~.
+ Responses (agent -> client), in request order:

  #+begin_src json
  {"id": N, "ok": ...}
  {"id": N, "err": {"code": "...", "message": "..."}}
  #+end_src

+ Malformed lines get ~{"err": {"code": "parse", ...}}~ (no ~id~).
+ Non-object JSON is a framing error, even if valid JSON.
+ Empty lines are ignored.  ~{"cmd": "quit"}~ gets
  ~{"ok": {"bye": true}}~ and the agent exits.
+ The agent is single-threaded: requests are handled in order and
  responses are correlated by ~id~.

* Error codes

| ~parse~           | Line is not a JSON object.                            |
| ~unknown_command~ | Unknown ~cmd~.                                        |
| ~not_initialized~ | Command requires ~initialize~ first.                  |
| ~crypto~          | Any crypto/store/parameter failure; ~message~ details. |

* Commands

** ~hello~

#+begin_src json
{"id": 1, "cmd": "hello"}
{"id": 1, "ok": {"protocol_version": 1}}
#+end_src

** ~initialize~

Creates or reopens the OlmMachine for the user's device, backed by a
SQLite crypto store.  The store directory is created if missing.  The
agent holds exactly one machine.

Identity rules (a device's crypto identity must never be reused under
another device):

+ The STORE PATH IS PER DEVICE (the client passes
  ~crypto/<user>/<device-id>/~).  If the store at that path belongs to
  a different user or device, ~initialize~ fails
  (~MismatchedAccount~).
+ A legacy store (a database directly in the parent directory)
  belonging to the SAME user and device is migrated into the per-device
  path automatically.  A legacy store belonging to a different device
  is left alone (the new device gets a fresh store).
+ Fresh client logins MUST NOT claim a device ID: a fresh login is a
  new device identity, and re-claiming a removed device's ID would
  resurrect its verified keys.  Only session restoration (resuming a
  saved session, or a soft logout) reuses a device identity.  After a
  hard logout (a revoked token with ~soft_logout: false~), the client
  discards the device's store.

#+begin_src json
{"id": 2, "cmd": "initialize", "params": {
  "user_id": "@bob:example.org", "device_id": "BOBDEVICE",
  "store_path": "~/.local/share/leman/crypto/"}}
{"id": 2, "ok": {"user_id": "...", "device_id": "...",
                 "identity_keys": {"curve25519": "<base64>", "ed25519": "<base64>"}}}
#+end_src

** ~outgoing_requests~

Returns the HTTP requests the state machine wants performed, as
~{method, path, body}~ triples.  ~body~ is the request body
pre-encoded as a JSON string: elisp cannot represent empty JSON
objects, so round-tripping a serialized body through elisp would
corrupt it (e.g. ~"timeout":null~ becoming ~"timeout":{}~).  The
client performs the request verbatim with its own authentication
and reports the result with ~mark_request_as_sent~.  Requests may
be re-returned if not yet marked as sent.

#+begin_src json
{"id": 3, "cmd": "outgoing_requests"}
{"id": 3, "ok": {"requests": [
  {"id": "<request-id>", "method": "POST",
   "path": "/_matrix/client/v3/keys/upload", "body": "{\"device_keys\":{...}}"},
  {"id": "<request-id>", "method": "PUT",
   "path": "/_matrix/client/v3/sendToDevice/m.room.encrypted/<txn>", "body": "{...}"}]}}
#+end_src

** ~mark_request_as_sent~

The ~request_id~ must match a previously returned request; the agent
remembers which kind it was.  ~response~ is the homeserver's JSON
response body for that request.

#+begin_src json
{"id": 4, "cmd": "mark_request_as_sent", "params": {
  "request_id": "<request-id>",
  "response": {"one_time_key_counts": {"signed_curve25519": 100}}}}
{"id": 4, "ok": {}}
#+end_src

** ~receive_sync_changes~

Feeds the E2EE parts of a ~/sync~ response into the machine.  Returns
the to-device events with encrypted ones decrypted, plus any new
outgoing requests.

/Ordering requirement: this must be called before the client persists
the ~next_batch~ token of the sync response, or to-device events (room
keys) can be lost./

/Zeroized keys: room keys (~m.room_key~) are returned with an empty
~session_key~: key material never leaves the machine (it is kept in
the store and used internally for decryption).  Clients must not rely
on the key material being present in returned events./

#+begin_src json
{"id": 5, "cmd": "receive_sync_changes", "params": {
  "to_device_events": [{"sender": "...", "type": "m.room.encrypted", "content": {...}}],
  "changed_devices": {"changed": [], "left": []},
  "one_time_keys_count": {"signed_curve25519": 100},
  "unused_fallback_keys": [],
  "next_batch_token": "s42"}}
{"id": 5, "ok": {"to_device_events": [<decrypted/processed events>],
                 "outgoing_requests": [...]}}
#+end_src

** ~decrypt_room_event~

Decrypts a ~m.room.encrypted~ room event (Megolm).  ~event~ is the
full event JSON (~sender~, ~event_id~, ~origin_server_ts~, ~type~,
~room_id~, ~content~).  On success the inner event is returned.

#+begin_src json
{"id": 6, "cmd": "decrypt_room_event", "params": {
  "room_id": "!room:example.org",
  "event": {"sender": "...", "event_id": "...", "type": "m.room.encrypted",
            "origin_server_ts": 0, "room_id": "...", "content": {...}}}}
{"id": 6, "ok": {"event": {"type": "m.room.message", "content": {...}, ...}}}
#+end_src

Failure (~session_not_found~ et al.) comes back as ~{"err": ...}~;
the client should keep the encrypted event and retry when keys arrive
(e.g. after ~receive_sync_changes~).

** ~update_tracked_users~

Marks users as tracked (their device lists will be followed; needed
before encryption).

#+begin_src json
{"id": 7, "cmd": "update_tracked_users", "params": {"users": ["@alice:example.org"]}}
{"id": 7, "ok": {}}
#+end_src

** ~quit~

#+begin_src json
{"id": 99, "cmd": "quit"}
{"id": 99, "ok": {"bye": true}}
#+end_src

* Sync flow (client side)

1. ~outgoing_requests~ -> perform each -> ~mark_request_as_sent~.
2. ~/sync~.
3. ~receive_sync_changes~ with the sync's E2EE parts.
4. ~outgoing_requests~ -> perform -> ~mark_request_as_sent~.
5. Decrypt room events via ~decrypt_room_event~; render room keys and
   membership updates via ~update_tracked_users~ and state events.
6. Persist ~next_batch~ only after step 3 completed.

* Security notes

+ The crypto store on disk is unencrypted (same trade-off as
  a MITM proxy could see); it must live in a user-private directory
  (0700).
+ The agent holds the account pickle in memory; clients should not
  expose the agent's stdio.
+ Key import/export (passphrase-encrypted) and verification arrive
  with phases E2/E3; until then, devices are trust-on-first-use at
  the UI level.

* Planned (E2+)

+ ~export_keys~/~import_keys~: room key export files.
+ Verification commands (emoji/QR SAS via MSC4108).

* E2: encrypting outgoing events (implemented 2026-09-13)

** ~encrypt_room_event~

Encrypts an event's content with Megolm for ROOM-ID.  The client
passes the room's member user IDs (~users~), which the machine needs
to track devices for key sharing (the client should have called
~update_tracked_users~ with them beforehand).  Content is the
plaintext event content; the agent never sees it after encryption
(the plaintext is not persisted).

#+begin_src json
{"id": 8, "cmd": "encrypt_room_event", "params": {
  "room_id": "!room:example.org",
  "event_type": "m.room.message",
  "content": {"msgtype": "m.text", "body": "hello"},
  "users": ["@alice:example.org"]}}
#+end_src

Two possible responses.  If the machine is missing Olm sessions with
some member devices, the keys must be claimed first:

#+begin_src json
{"id": 8, "ok": {"status": "claims_pending"}}
#+end_src

The client then performs the pending ~keys/claim~ (and any other)
outgoing requests, marks them as sent, and retries the command.  Once
sessions exist, the agent shares a room key with the members' devices
(the ~sendToDevice~ requests appear in ~outgoing_requests~ and must
be performed before other clients can decrypt) and encrypts:

#+begin_src json
{"id": 8, "ok": {"status": "ok", "event": {
  "type": "m.room.encrypted",
  "content": {"algorithm": "m.megolm.v1.aes-sha2", "ciphertext": "...",
              "sender_key": "...", "session_id": "..."}}}}
#+end_src

The client sends the returned event via
~PUT /rooms/{room_id}/send/m.room.encrypted/{txn_id}~ with its own
transaction ID; this request is an ordinary API request, not an
agent outgoing request.

Retry policy: the client retries while the status is
~claims_pending~, performing outgoing requests between attempts,
bounded (e.g. 3 attempts) to avoid loops.

** Send flow (client side)

1. Check the room is encrypted (~m.room.encryption~ state event).
2. ~update_tracked_users~ with the room's member IDs.
3. Pump outgoing requests (the keys/query queued by step 2 must
   complete first, or the room key would be shared with nobody).
4. ~encrypt_room_event~ (retry on ~claims_pending~, pumping outgoing
   requests between attempts).
5. ~PUT .../send/m.room.encrypted/{txn}~ with the encrypted event.
6. Pump outgoing requests once more (key distribution continues in
   the background for newly seen devices).

* E3: device verification (implemented 2026-09-13; emoji SAS)

Verification uses the state machine's interactive verification
(SAS/emoji).  All verification traffic is to-device events: they
flow through ~receive_sync_changes~ on the way in and through
~outgoing_requests~ on the way out, like everything else; no new
transport is needed.  Verification flow IDs are not unique across
users, so most commands take both ~user_id~ and ~flow_id~.

** ~devices~

Lists a user's known devices (the machine's own user by default).

#+begin_src json
{"id": 10, "cmd": "devices", "params": {"user_id": "@user:example.com"}}
{"id": 10, "ok": {"devices": [
  {"device_id": "ABC", "display_name": "Element X",
   "verified": false, "deleted": false}]}}
#+end_src

~verified~ is the device's trust state (signature and cross-signing
checks, plus local trust).

** ~request_verification~

Starts verifying DEVICE of USER (typically another device of the
machine's own user).  The ~m.key.verification.request~ flows out via
~outgoing_requests~.  Returns the flow ID.

#+begin_src json
{"id": 11, "cmd": "request_verification", "params": {
  "user_id": "@user:example.com", "device_id": "ABC"}}
{"id": 11, "ok": {"flow_id": "<flow-id>"}}
#+end_src

** ~verification_requests~

Lists the known verification requests (incoming and outgoing),
including whether a SAS object exists for the request (their start
has been received).

#+begin_src json
{"id": 12, "cmd": "verification_requests"}
{"id": 12, "ok": {"requests": [{
  "flow_id": "<flow-id>", "user_id": "@user:example.com",
  "device_id": "ABC", "state": "ready", "we_started": false,
  "sas": false}]}}
#+end_src

~state~ is one of ~created~, ~ready~, ~accepted~, ~done~,
~cancelled~ (as seen by us).

** ~import_cross_signing_keys~

Imports the account's private cross-signing keys (the unpadded
base64 seeds stored in secret storage under the
~m.cross_signing.*~ secrets).  Without them the machine cannot
sign anything: devices verified via SAS are never signed (other
clients then show them as unverified and their verification flows
wait for our signature), and backup versions the machine creates
carry no master-key signature, so other clients do not trust
them.

#+begin_src json
{"id": 13, "cmd": "import_cross_signing_keys", "params": {
  "master_key": "<unpadded-base64>",
  "self_signing_key": "<unpadded-base64>",
  "user_signing_key": "<unpadded-base64>"}}
{"id": 13, "ok": {"has_master": true, "has_self_signing": true,
                  "has_user_signing": true}}
#+end_src

** ~cross_signing_status~

Reports which private cross-signing keys the machine holds.

#+begin_src json
{"id": 14, "cmd": "cross_signing_status"}
{"id": 14, "ok": {"has_master": false, "has_self_signing": false,
                  "has_user_signing": false}}
#+end_src

** ~accept_verification~

Accepts an incoming request (sends ~m.key.verification.ready~).

#+begin_src json
{"id": 13, "cmd": "accept_verification", "params": {
  "user_id": "@user:example.com", "flow_id": "<flow-id>"}}
{"id": 13, "ok": {}}
#+end_src

** ~start_sas~

Starts SAS for the request (sends ~m.key.verification.start~).
For an incoming request whose start we already received, the SAS
object already exists (and our ~accept~ is queued); the command
then just reports it.

#+begin_src json
{"id": 14, "cmd": "start_sas", "params": {
  "user_id": "@user:example.com", "flow_id": "<flow-id>"}}
{"id": 14, "ok": {"flow_id": "<flow-id>"}}
#+end_src

** ~verification_sas~

Reports the SAS state for the flow.  ~can_be_presented~ is true
once both sides have exchanged keys and the emoji can be shown;
~accepted~ is true once we have accepted their start.

#+begin_src json
{"id": 15, "cmd": "verification_sas", "params": {
  "user_id": "@user:example.com", "flow_id": "<flow-id>"}}
{"id": 15, "ok": {"can_be_presented": true, "accepted": true,
                  "done": false, "cancelled": false,
                  "cancel_code": null, "cancel_reason": null,
                  "cancelled_by_us": null,
                  "emoji": [{"number": 49, "symbol": "🦋",
                             "description": "butterfly"}, ...]}}
#+end_src

~emoji~ is present (7 items) only when ~can_be_presented~.  When
~cancelled~ is true, ~cancel_code~ (e.g. ~m.mismatched_sas~),
~cancel_reason~ (human-readable), and ~cancelled_by_us~ describe
the cancellation.

** ~accept_sas~

Accepts their start (sends ~m.key.verification.accept~).  Only
needed for flows where they started the SAS.

#+begin_src json
{"id": 16, "cmd": "accept_sas", "params": {
  "user_id": "@user:example.com", "flow_id": "<flow-id>"}}
{"id": 16, "ok": {}}
#+end_src

** ~confirm_sas~

Confirms the short authentication string matches (sends
~m.key.verification.mac~; a signature upload may follow via
~outgoing_requests~).

#+begin_src json
{"id": 17, "cmd": "confirm_sas", "params": {
  "user_id": "@user:example.com", "flow_id": "<flow-id>"}}
{"id": 17, "ok": {}}
#+end_src

** ~cancel_verification~

Cancels the request or SAS.

#+begin_src json
{"id": 18, "cmd": "cancel_verification", "params": {
  "user_id": "@user:example.com", "flow_id": "<flow-id>"}}
{"id": 18, "ok": {}}
#+end_src

** Verification flow (client side)

1. ~devices~ to pick the device to verify (or notice an incoming
   request via ~verification_requests~ after each sync).
2. ~request_verification~ (outgoing) or ~accept_verification~
   (incoming).
3. ~start_sas~ when the request is ready.
4. When ~verification_sas~ reports ~can_be_presented~, show the 7
   emoji and let the user compare with the other device.
5. ~confirm_sas~ or ~cancel_verification~.
6. Pump ~outgoing_requests~ throughout (all verification traffic is
   ordinary outgoing requests); the peer's events arrive via sync and
   ~receive_sync_changes~, so each step may need a sync in between.

* E4: key backup and secret storage (SSSS)

Backing up room keys to the homeserver (Megolm backup v1) so that a
new device can restore its message history, and storing the backup's
decryption key in SSSS (secret storage) under the standard
~m.megolm_backup.v1~ secret name (Element interoperates with this).

Two distinct keys are involved, as in the rest of the Matrix
ecosystem:

+ the *backup decryption key* (curve25519, shown to the user as the
  backup's recovery key in base58; its private half decrypts the
  backup), and
+ the *SSSS default key* (aes-hmac-sha2, shown as the secret-storage
  recovery key in base58; it encrypts secrets in account data).

For the backup's auth data the device signs with its ed25519 key.

All commands below are agent commands; the client performs the
corresponding HTTP calls (room_keys, account data) — same split as
everywhere else.

** ~backup_create~

Generates a fresh backup decryption key and the signed auth data for
a new backup version.  (Device-side; the client creates the version
on the server with these.)

#+begin_src json
{"id": 20, "cmd": "backup_create"}
{"id": 20, "ok": {
  "recovery_key": "<base58>",
  "algorithm": "m.megolm_backup.v1.curve25519-aes-sha2",
  "auth_data": {"public_key": "<base64>", "signatures": {...}}}}
#+end_src

** ~backup_enable~

Imports a backup decryption key (base58) and enables backing up
future room keys for VERSION.  Also used by a NEW device to adopt a
backup for restoring.

#+begin_src json
{"id": 21, "cmd": "backup_enable", "params": {
  "recovery_key": "<base58>", "version": "<version>"}}
{"id": 21, "ok": {}}
#+end_src

** ~backup_verify~

Checks whether a recovery key matches a backup (the full
~m.room_key.backup~ account-data content, ~algorithm~ + ~auth_data~).
The client calls this before adopting a backup.

#+begin_src json
{"id": 22, "cmd": "backup_verify", "params": {
  "recovery_key": "<base58>",
  "backup_info": {"algorithm": "...", "auth_data": {...}}}
{"id": 22, "ok": {"matches": true}}
#+end_src

** ~backup_status~

#+begin_src json
{"id": 23, "cmd": "backup_status"}
{"id": 23, "ok": {
  "enabled": true, "version": "<version>",
  "room_key_counts": {"total": 42, "backed_up": 40}}}
#+end_src

** ~backup_room_keys~

Encrypts the not-yet-backed-up room keys.  Returns a request for
~PUT /room_keys/keys?version=<version>~ (body is a pre-encoded JSON
string), or null when there is nothing to back up.

#+begin_src json
{"id": 24, "cmd": "backup_room_keys"}
{"id": 24, "ok": {"request": {
  "id": "<txn-id>",
  "path": "/_matrix/client/v3/room_keys/keys",
  "params": {"version": "<version>"},
  "body": "{...}"}}}
#+end_src

** ~backup_mark_as_sent~

Reports that a backup request was performed.

#+begin_src json
{"id": 25, "cmd": "backup_mark_as_sent", "params": {"id": "<txn-id>"}}
{"id": 25, "ok": {}}
#+end_src

** ~backup_import~

Imports room keys downloaded with
~GET /room_keys/keys?version=<version>~ (the ~rooms~ object of the
response, as JSON).  The recovery key decrypts the sessions' session
data.

#+begin_src json
{"id": 26, "cmd": "backup_import", "params": {
  "recovery_key": "<base58>", "rooms": {...}}}
{"id": 26, "ok": {"imported": 30, "total": 30}}
#+end_src

** ~ssss_create~

Generates the secret storage default key.

#+begin_src json
{"id": 27, "cmd": "ssss_create"}
{"id": 27, "ok": {
  "key_id": "<id>",
  "recovery_key": "<base58>",
  "content": {"algorithm": "m.secret_storage.v1.aes-hmac-sha2",
              "iv": "...", "mac": "..."}}}
#+end_src

The client uploads ~content~ as the ~m.secret_storage.key.<key_id>~
account data and ~{"key": "<key_id>"}~ as
~m.secret_storage.default_key~.

** ~ssss_encrypt_secret~ / ~ssss_decrypt_secret~

Encrypts/decrypts a named secret with the SSSS key.  NAME is the
secret's name (e.g. ~m.megolm_backup.v1~).  The encrypted data
({~ciphertext~, ~iv~, ~mac~}) is stored as the
~m.secret_storage.secret.<name>~ account data.

#+begin_src json
{"id": 28, "cmd": "ssss_encrypt_secret", "params": {
  "key_id": "<id>", "recovery_key": "<base58>",
  "name": "m.megolm_backup.v1", "secret": "<base64>"}}
{"id": 28, "ok": {"iv": "...", "ciphertext": "...", "mac": "..."}}

{"id": 29, "cmd": "ssss_decrypt_secret", "params": {
  "key_id": "<id>", "recovery_key": "<base58>",
  "name": "m.megolm_backup.v1",
  "iv": "...", "ciphertext": "...", "mac": "..."}}
{"id": 29, "ok": {"secret": "<base64>"}}
#+end_src

The ~m.megolm_backup.v1~ secret's plaintext is the base58 backup
decryption key.

** ~ssss_check_key~

Checks whether a recovery key unlocks the SSSS key described by
KEY_CONTENT (the zero-message MAC check); errs otherwise.  The
client uses this to verify a recovery key before adopting an
existing secret-storage setup.

#+begin_src json
{"id": 30, "cmd": "ssss_check_key", "params": {
  "key_id": "<id>", "recovery_key": "<base58>", "key_content": {...}}}
{"id": 30, "ok": {"valid": true}}
#+end_src

** ~backup_recovery_key~

Returns the backup decryption key the machine has saved (its
base58 recovery key), or null when none is saved.  Lets the
client re-store the key under another secret-storage key without
asking the user to type it again.

#+begin_src json
{"id": 31, "cmd": "backup_recovery_key"}
{"id": 31, "ok": {"recovery_key": "<base58>"}}
#+end_src

** ~export_room_keys~ / ~import_room_keys~

Exports every room key the machine holds to, and imports room
keys from, an encrypted key-export file: the same format as
Element's "Export E2E room keys" (the file's content is passed as
a string; PASSPHRASE unlocks it).  Imported keys are not marked
as backed up, so an enabled backup picks them up.

#+begin_src json
{"id": 32, "cmd": "export_room_keys", "params": {"passphrase": "..."}}
{"id": 32, "ok": {"keys": "-----BEGIN MEGOLM SESSION DATA-----\n..."}}

{"id": 33, "cmd": "import_room_keys", "params": {
  "keys": "-----BEGIN MEGOLM SESSION DATA-----\n...", "passphrase": "..."}}
{"id": 33, "ok": {"imported": 12, "total": 12}}
#+end_src

** Client flows

Setup (a device that has room keys):

1. ~backup_create~ → ~POST /room_keys/version~ with the returned
   ~algorithm~ and ~auth_data~ → the response gives the ~version~.
2. ~backup_enable~ with the recovery key and version.
3. ~ssss_create~ → upload the default key and key content account
   data → ~ssss_encrypt_secret~ with the backup's recovery key →
   upload ~m.secret_storage.secret.m.megolm_backup.v1~.
4. Loop ~backup_room_keys~ → perform the request → ~backup_mark_as_sent~,
   until there is nothing left to back up; repeat after syncs.

Restore (a new device, e.g. after a fresh login):

1. Read account data: ~m.secret_storage.default_key~,
   ~m.secret_storage.key.<key_id>~,
   ~m.secret_storage.secret.m.megolm_backup.v1~, and
   ~m.room_key.backup~ (the version's auth data).
2. Ask the user for the secret-storage recovery key.
3. ~ssss_decrypt_secret~ → the base58 backup decryption key.
4. ~backup_verify~ against ~m.room_key.backup~'s auth data; if it
   matches, ~backup_enable~ with the backup's version.
5. ~GET /room_keys/keys?version=<version>~ → ~backup_import~.

The client surfaces a ~leman-e2ee-restore-keys~ command for the
restore flow and backs up keys periodically after syncs.
