#+TITLE: Leman E2EE Agent Protocol

The protocol between Leman.el (the client) and the ~leman-agent~
subprocess (the agent), which wraps the ~matrix-sdk-crypto~ state
machine.  Protocol version 1.

* Framing

+ One JSON object per line, UTF-8, over the agent's stdin/stdout.
+ Requests (client -> agent): ~{"id": N, "cmd": "...", "params": ...}~.
+ Responses (agent -> client), in request order:

  #+begin_src json
  {"id": N, "ok": ...}
  {"id": N, "err": {"code": "...", "message": "..."}}
  #+end_src

+ Malformed lines get ~{"err": {"code": "parse", ...}}~ (no ~id~).
+ Non-object JSON is a framing error, even if valid JSON.
+ Empty lines are ignored.  ~{"cmd": "quit"}~ gets
  ~{"ok": {"bye": true}}~ and the agent exits.
+ The agent is single-threaded: requests are handled in order and
  responses are correlated by ~id~.

* Error codes

| ~parse~           | Line is not a JSON object.                            |
| ~unknown_command~ | Unknown ~cmd~.                                        |
| ~not_initialized~ | Command requires ~initialize~ first.                  |
| ~crypto~          | Any crypto/store/parameter failure; ~message~ details. |

* Commands

** ~hello~

#+begin_src json
{"id": 1, "cmd": "hello"}
{"id": 1, "ok": {"protocol_version": 1}}
#+end_src

** ~initialize~

Creates or reopens the OlmMachine for the user's device, backed by a
SQLite crypto store.  The store directory is created if missing.  The
agent holds exactly one machine.

#+begin_src json
{"id": 2, "cmd": "initialize", "params": {
  "user_id": "@bob:example.org", "device_id": "BOBDEVICE",
  "store_path": "~/.local/share/leman/crypto/"}}
{"id": 2, "ok": {"user_id": "...", "device_id": "...",
                 "identity_keys": {"curve25519": "<base64>", "ed25519": "<base64>"}}}
#+end_src

** ~outgoing_requests~

Returns the HTTP requests the state machine wants performed, as
~{method, path, body}~ triples.  ~body~ is the request body
pre-encoded as a JSON string: elisp cannot represent empty JSON
objects, so round-tripping a serialized body through elisp would
corrupt it (e.g. ~"timeout":null~ becoming ~"timeout":{}~).  The
client performs the request verbatim with its own authentication
and reports the result with ~mark_request_as_sent~.  Requests may
be re-returned if not yet marked as sent.

#+begin_src json
{"id": 3, "cmd": "outgoing_requests"}
{"id": 3, "ok": {"requests": [
  {"id": "<request-id>", "method": "POST",
   "path": "/_matrix/client/v3/keys/upload", "body": "{\"device_keys\":{...}}"},
  {"id": "<request-id>", "method": "PUT",
   "path": "/_matrix/client/v3/sendToDevice/m.room.encrypted/<txn>", "body": "{...}"}]}}
#+end_src

** ~mark_request_as_sent~

The ~request_id~ must match a previously returned request; the agent
remembers which kind it was.  ~response~ is the homeserver's JSON
response body for that request.

#+begin_src json
{"id": 4, "cmd": "mark_request_as_sent", "params": {
  "request_id": "<request-id>",
  "response": {"one_time_key_counts": {"signed_curve25519": 100}}}}
{"id": 4, "ok": {}}
#+end_src

** ~receive_sync_changes~

Feeds the E2EE parts of a ~/sync~ response into the machine.  Returns
the to-device events with encrypted ones decrypted, plus any new
outgoing requests.

/Ordering requirement: this must be called before the client persists
the ~next_batch~ token of the sync response, or to-device events (room
keys) can be lost./

/Zeroized keys: room keys (~m.room_key~) are returned with an empty
~session_key~: key material never leaves the machine (it is kept in
the store and used internally for decryption).  Clients must not rely
on the key material being present in returned events./

#+begin_src json
{"id": 5, "cmd": "receive_sync_changes", "params": {
  "to_device_events": [{"sender": "...", "type": "m.room.encrypted", "content": {...}}],
  "changed_devices": {"changed": [], "left": []},
  "one_time_keys_count": {"signed_curve25519": 100},
  "unused_fallback_keys": [],
  "next_batch_token": "s42"}}
{"id": 5, "ok": {"to_device_events": [<decrypted/processed events>],
                 "outgoing_requests": [...]}}
#+end_src

** ~decrypt_room_event~

Decrypts a ~m.room.encrypted~ room event (Megolm).  ~event~ is the
full event JSON (~sender~, ~event_id~, ~origin_server_ts~, ~type~,
~room_id~, ~content~).  On success the inner event is returned.

#+begin_src json
{"id": 6, "cmd": "decrypt_room_event", "params": {
  "room_id": "!room:example.org",
  "event": {"sender": "...", "event_id": "...", "type": "m.room.encrypted",
            "origin_server_ts": 0, "room_id": "...", "content": {...}}}}
{"id": 6, "ok": {"event": {"type": "m.room.message", "content": {...}, ...}}}
#+end_src

Failure (~session_not_found~ et al.) comes back as ~{"err": ...}~;
the client should keep the encrypted event and retry when keys arrive
(e.g. after ~receive_sync_changes~).

** ~update_tracked_users~

Marks users as tracked (their device lists will be followed; needed
before encryption).

#+begin_src json
{"id": 7, "cmd": "update_tracked_users", "params": {"users": ["@alice:example.org"]}}
{"id": 7, "ok": {}}
#+end_src

** ~quit~

#+begin_src json
{"id": 99, "cmd": "quit"}
{"id": 99, "ok": {"bye": true}}
#+end_src

* Sync flow (client side)

1. ~outgoing_requests~ -> perform each -> ~mark_request_as_sent~.
2. ~/sync~.
3. ~receive_sync_changes~ with the sync's E2EE parts.
4. ~outgoing_requests~ -> perform -> ~mark_request_as_sent~.
5. Decrypt room events via ~decrypt_room_event~; render room keys and
   membership updates via ~update_tracked_users~ and state events.
6. Persist ~next_batch~ only after step 3 completed.

* Security notes

+ The crypto store on disk is unencrypted (same trade-off as
  Pantalaimon); it must live in a user-private directory (0700).
+ The agent holds the account pickle in memory; clients should not
  expose the agent's stdio.
+ Key import/export (passphrase-encrypted) and verification arrive
  with phases E2/E3; until then, devices are trust-on-first-use at
  the UI level.

* Planned (E2+)

+ ~export_keys~/~import_keys~: room key export files.
+ Verification commands (emoji/QR SAS via MSC4108).

* E2: encrypting outgoing events (specified, in development)

** ~encrypt_room_event~

Encrypts an event's content with Megolm for ROOM-ID.  The client
passes the room's member user IDs (~users~), which the machine needs
to track devices for key sharing (the client should have called
~update_tracked_users~ with them beforehand).  Content is the
plaintext event content; the agent never sees it after encryption
(the plaintext is not persisted).

#+begin_src json
{"id": 8, "cmd": "encrypt_room_event", "params": {
  "room_id": "!room:example.org",
  "event_type": "m.room.message",
  "content": {"msgtype": "m.text", "body": "hello"},
  "users": ["@alice:example.org"]}}
#+end_src

Two possible responses.  If the machine is missing Olm sessions with
some member devices, the keys must be claimed first:

#+begin_src json
{"id": 8, "ok": {"status": "claims_pending"}}
#+end_src

The client then performs the pending ~keys/claim~ (and any other)
outgoing requests, marks them as sent, and retries the command.  Once
sessions exist, the agent shares a room key with the members' devices
(the ~sendToDevice~ requests appear in ~outgoing_requests~ and must
be performed before other clients can decrypt) and encrypts:

#+begin_src json
{"id": 8, "ok": {"status": "ok", "event": {
  "type": "m.room.encrypted",
  "content": {"algorithm": "m.megolm.v1.aes-sha2", "ciphertext": "...",
              "sender_key": "...", "session_id": "..."}}}}
#+end_src

The client sends the returned event via
~PUT /rooms/{room_id}/send/m.room.encrypted/{txn_id}~ with its own
transaction ID; this request is an ordinary API request, not an
agent outgoing request.

Retry policy: the client retries while the status is
~claims_pending~, performing outgoing requests between attempts,
bounded (e.g. 3 attempts) to avoid loops.

** Send flow (client side)

1. Check the room is encrypted (~m.room.encryption~ state event).
2. ~update_tracked_users~ with the room's member IDs.
3. Pump outgoing requests (the keys/query queued by step 2 must
   complete first, or the room key would be shared with nobody).
4. ~encrypt_room_event~ (retry on ~claims_pending~, pumping outgoing
   requests between attempts).
5. ~PUT .../send/m.room.encrypted/{txn}~ with the encrypted event.
6. Pump outgoing requests once more (key distribution continues in
   the background for newly seen devices).

* E3: device verification (specified, in development)

Verification uses the state machine's interactive verification
(SAS/emoji).  All verification traffic is to-device events: they
flow through ~receive_sync_changes~ on the way in and through
~outgoing_requests~ on the way out, like everything else; no new
transport is needed.  Verification flow IDs are not unique across
users, so most commands take both ~user_id~ and ~flow_id~.

** ~devices~

Lists a user's known devices (the machine's own user by default).

#+begin_src json
{"id": 10, "cmd": "devices", "params": {"user_id": "@vv:hobeika.fr"}}
{"id": 10, "ok": {"devices": [
  {"device_id": "ABC", "display_name": "Element X",
   "verified": false, "deleted": false}]}}
#+end_src

~verified~ is the device's trust state (signature and cross-signing
checks, plus local trust).

** ~request_verification~

Starts verifying DEVICE of USER (typically another device of the
machine's own user).  The ~m.key.verification.request~ flows out via
~outgoing_requests~.  Returns the flow ID.

#+begin_src json
{"id": 11, "cmd": "request_verification", "params": {
  "user_id": "@vv:hobeika.fr", "device_id": "ABC"}}
{"id": 11, "ok": {"flow_id": "<flow-id>"}}
#+end_src

** ~verification_requests~

Lists the known verification requests (incoming and outgoing),
including whether a SAS object exists for the request (their start
has been received).

#+begin_src json
{"id": 12, "cmd": "verification_requests"}
{"id": 12, "ok": {"requests": [{
  "flow_id": "<flow-id>", "user_id": "@vv:hobeika.fr",
  "device_id": "ABC", "state": "ready", "we_started": false,
  "sas": false}]}}
#+end_src

~state~ is one of ~created~, ~ready~, ~accepted~, ~done~,
~cancelled~ (as seen by us).

** ~accept_verification~

Accepts an incoming request (sends ~m.key.verification.ready~).

#+begin_src json
{"id": 13, "cmd": "accept_verification", "params": {
  "user_id": "@vv:hobeika.fr", "flow_id": "<flow-id>"}}
{"id": 13, "ok": {}}
#+end_src

** ~start_sas~

Starts SAS for the request (sends ~m.key.verification.start~).
For an incoming request whose start we already received, the SAS
object already exists (and our ~accept~ is queued); the command
then just reports it.

#+begin_src json
{"id": 14, "cmd": "start_sas", "params": {
  "user_id": "@vv:hobeika.fr", "flow_id": "<flow-id>"}}
{"id": 14, "ok": {"flow_id": "<flow-id>"}}
#+end_src

** ~verification_sas~

Reports the SAS state for the flow.  ~can_be_presented~ is true
once both sides have exchanged keys and the emoji can be shown;
~accepted~ is true once we have accepted their start.

#+begin_src json
{"id": 15, "cmd": "verification_sas", "params": {
  "user_id": "@vv:hobeika.fr", "flow_id": "<flow-id>"}}
{"id": 15, "ok": {"can_be_presented": true, "accepted": true,
                  "done": false, "cancelled": false,
                  "emoji": [{"number": 49, "symbol": "🦋",
                             "description": "butterfly"}, ...]}}
#+end_src

~emoji~ is present (7 items) only when ~can_be_presented~.

** ~accept_sas~

Accepts their start (sends ~m.key.verification.accept~).  Only
needed for flows where they started the SAS.

#+begin_src json
{"id": 16, "cmd": "accept_sas", "params": {
  "user_id": "@vv:hobeika.fr", "flow_id": "<flow-id>"}}
{"id": 16, "ok": {}}
#+end_src

** ~confirm_sas~

Confirms the short authentication string matches (sends
~m.key.verification.mac~; a signature upload may follow via
~outgoing_requests~).

#+begin_src json
{"id": 17, "cmd": "confirm_sas", "params": {
  "user_id": "@vv:hobeika.fr", "flow_id": "<flow-id>"}}
{"id": 17, "ok": {}}
#+end_src

** ~cancel_verification~

Cancels the request or SAS.

#+begin_src json
{"id": 18, "cmd": "cancel_verification", "params": {
  "user_id": "@vv:hobeika.fr", "flow_id": "<flow-id>"}}
{"id": 18, "ok": {}}
#+end_src

** Verification flow (client side)

1. ~devices~ to pick the device to verify (or notice an incoming
   request via ~verification_requests~ after each sync).
2. ~request_verification~ (outgoing) or ~accept_verification~
   (incoming).
3. ~start_sas~ when the request is ready.
4. When ~verification_sas~ reports ~can_be_presented~, show the 7
   emoji and let the user compare with the other device.
5. ~confirm_sas~ or ~cancel_verification~.
6. Pump ~outgoing_requests~ throughout (all verification traffic is
   ordinary outgoing requests); the peer's events arrive via sync and
   ~receive_sync_changes~, so each step may need a sync in between.

+ Key backup commands (SSSS).
